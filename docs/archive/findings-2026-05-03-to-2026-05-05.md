## 2026-05-05 Source-Chain Audit Findings

- 本轮目标不是继续修功能，而是基于 live 代码重新做 Reader vs Legado 书源链路差异审计，并输出两份新文档：`docs/ReaderLegadoSourceChainDiffAudit.md` 与 `docs/ReaderHardcodingAndBugAudit.md`。
- Reader 当前最大差异面不是基础 CSS/XPath/JSONPath 解析，而是请求状态语义：`enabledCookieJar`、登录头、`loginCheckJs`、`AnalyzeUrl` 高级 option、正文 `webJs/sourceRegex/imageDecode/payAction` 等没有完整对齐 Legado。
- `ScriptIntegration.LoginCheck()` 虽然存在，但当前生产链路没有统一复用；搜索/发现/详情手写了简化版 body 替换逻辑，目录和正文则完全没接 `loginCheckJs`，这是高优先级真实 bug。
- `cmd/server/main.go` 当前给所有链路注入一个共享 `script.Runtime`；而 `runtime.EvalWithBindings()` 会把 `policy.SourceKey` 写回 runtime 自身，后续不再按当前 source 重新计算。这会导致缓存/`java.get`/`java.put` namespace 跨书源串扰，是高优先级实现 bug。
- Reader 当前生产代码里几乎没有按域名或书源名写死的分支；source-specific 逻辑主要集中在 `test/e2e/real_source_collection_test.go` 的候选关键词和特征标注，不在生产 API 路径。
- `enabledCookieJar` 现在只是“字段已导入、已落库、已回传”，并没有按书源控制 fetcher cookie 行为；全局 `HTTPFetcher` 只要挂了 `CookieManager`，所有请求都会统一 `Load/Save` cookies。
- Reader `cookieDomain()` 只取 host 最后两段；Legado `NetworkUtils.getSubDomain()` 使用 public suffix 数据库求 effective TLD+1，因此 `.com.cn` 等域名在 Reader 中会错域。
- 搜索/发现/目录链路没有完整复刻 Legado `bookList/chapterList` 的 `+/-` 前缀顺序语义；目录链虽然剥掉了前缀，但没有执行 reverse。
- `Analyzer.vars` 是实例级 map，搜索结果列表、发现列表、目录列表都复用了同一个 Analyzer 实例，当前存在 `@put` 变量跨条目污染风险。
- `coverDecodeJs`、`exploreScreen`、`loginUrl/loginUi`、`ruleReview`、文件源 `downloadUrls` 等字段在 Reader 中有明显的“字段保留但行为未闭环”现象，需在审计文档里按“设计性保留 / 未实现 / 当前 bug”分类说明。

## 2026-05-03 Real Source Chain Findings

- 真实集合 E2E 当前可下载并解析 459 条书源，导入 459 条；报告文件为 `test/reports/real_source_collection_e2e_report.json` 和 `.md`。
- Legado `AnalyzeRule.getString(ruleStr)` 在 `ruleStr` 为空时直接返回空字符串；Reader 之前的 `Analyzer.GetString("", input)` 会把 `input` 原样返回，导致详情页 HTML 被写进空字段。
- Legado `BookInfo.analyzeBookInfo` 对 `tocUrl` 的语义是 `analyzeRule.getString(infoRule.tocUrl, isUrl = true)`；为空时回退 `baseUrl`，并可缓存当前详情 HTML。Reader 之前在 `ruleBookInfo.tocUrl` 缺失时把整页 HTML 写入 `Book.TocURL`，导致后续目录阶段把 HTML 当 URL fetch。
- Legado `splitSourceRule` 会用 `<js>...</js>|@js:...` 模式把规则串拆成多个 `SourceRule`，例如正文规则 `<js>...</js>$..content||$.message` 应先执行 JS，再把返回值交给 JSONPath。Reader 之前只识别“整个规则就是 JS”的情况，导致真实正文规则无法继续解析。
- `script.Runtime.Policy` 已支持 `Fetcher`，但 server 和 E2E wiring 没有注入 HTTP Fetcher，导致 `java.ajax/java.connect/java.get/java.post` 在真实正文 JS 中不可用，返回 `script_failed` 文本并触发后续 JS/JSONPath 错误。
- 修正后真实 E2E 报告显示 `得奇小说（优+++）` (`https://www.deqixs.co`, `src_4377e504b78dc41848314bf3`) 完成 `search -> info -> toc -> content`，`releaseAllowed=true`，正文阶段 `length=33`。
- 当前仍可见但不阻塞 release gate 的兼容/环境问题包括：部分源 HTTP 404、`JavaImporter` 未实现、部分 JS 超时、部分站点 TLS 证书不匹配或网络超时/连接重置。
- JS 引擎调研结论：继续使用 goja 是当前最稳妥路径。goja 是纯 Go、容易和现有 context timeout/interrupt/沙箱绑定集成；v8go 依赖 V8 原生运行时，部署和安全面更重；QuickJS Go binding 也引入 native runtime/CGO 复杂度。目标应优先补 Legado 绑定和规则语义，而不是更换 JS 引擎。
- 30 候选真实审计已支持 `READER_REAL_E2E_MAX_CANDIDATES` 和 `READER_REAL_E2E_CONTINUE_AFTER_SUCCESS=true`。当前结果仍是 1/30 完整成功，说明不能声称“大部分书源可用”。
- `cookie` 全局绑定补齐后，`cookie is not defined` 从 30 候选报告中消失；`{{cookie.removeCookie(...)}}` 这类副作用内联表达式返回 nil 时也已修正为空字符串，避免 `<nil>https://...` 污染 URL。
- Legado `AnalyzeRule.SourceRule` 支持 `@put:{...}` 将当前规则解析得到的变量写入书籍/章节/源变量域，并支持 `@get:{...}` 和 `{{...}}` 在后续规则里回填；真实 `番薯小说（优++）` 搜索规则依赖 `@put:{id:id,...}`，目录 URL 又依赖 `{{java.get('id')}}`。
- Legado JSON 内容上下文中，`SourceRule` 会因 `isJSON` 将普通规则按 JSONPath 处理；因此 `data[0].content` 这类不带 `$.` 前缀的裸路径在 JSON 响应正文中也应作为 `$.data[0].content` 解析。真实 `番薯小说（优++）` 正文规则即为 `data[0].content`。
- Legado `BookChapter.getAbsoluteURL` 会对 URL 主体绝对化并保留逗号后的自定义 URL 属性；后续 `AnalyzeUrl` 会解析 `method/body/headers`。真实 `全本小说（优++）` 与 `番薯小说（优++）` 的章节 URL 都是 `url,{"method":"POST","body":...}`，Reader 之前正文抓取按 GET 请求整串 URL，导致目标站点返回 404。
- 补齐变量跨阶段传递、JSON 裸路径和正文章节 URL option 后，30 候选真实审计提升为 `fullSuccessCount=3`；阶段摘要为搜索 5 passed/25 failed、详情 4 passed/1 failed、目录 3 passed/1 failed、正文 3 passed/0 failed。新增完整成功源为 `全本小说（优++）`（正文 15107 字）和 `番薯小说（优++）`（正文 9835 字）。
- `猫眼看书（优++）` 当前仍在目录阶段 `toc_empty`；其规则依赖 `$.data.list[*]` 和 `java.aesBase64DecodeToString(...)`，AES helper 已补但真实返回/列表结构仍需继续诊断。
- 100 候选真实审计中，`<js>...</js>` 内含 `{{...}}` 的 URL 规则会暴露 Reader 的规则优先级问题：Legado 先 `splitSourceRule` 拆 JS，再在 `SourceRule.makeUpRule` 中替换 `{{...}}`；Reader 之前在 `GetString` 入口看到 `{{` 就整体模板渲染，导致 JS URL 原文进入 Fetch 并报 URL 控制字符错误。
- 调整为 JS 规则优先后，相关源从 URL 解析失败推进到真实 HTTP 401 或后续规则阶段；这说明该问题属于实现缺口，且修复方向正确，但部分 API 源仍可能需要签名/Header/登录参数进一步兼容。
- 100 候选搜索失败中仍有明确 JS helper 缺口：`source.getVariable` 和 `java.HMacHex`。已补安全占位 `source.getVariable()/putVariable()` 与 `java.HMacHex(data, algorithm, key)`，覆盖常见 HmacSHA1/SHA256/SHA384/SHA512。
- 最新 100 候选审计摘要：`attemptedCandidates=100`、`fullSuccessCount=3`、`search passed=10 failed=90`、`info passed=7 failed=3`、`toc passed=4 failed=3`、`content passed=3 failed=1`。搜索失败中 40 条为整体 `context deadline exceeded`，其余主要为站点空结果、HTTP 400/403/404、JavaImporter 未实现、脚本语法/辅助函数缺口、TLS/连接重置/DNS 问题。

- 受限 `JavaImporter` 兼容层补齐后，真实 100 候选中的 `JavaImporter is not defined` 正文错误消失；七猫/API 类源推进到 `Cannot read property 'content' of undefined`，说明 runtime 已能执行 JavaImporter/AES 形态脚本，剩余问题是实际 `java.ajax` 请求返回结构/参数/header/认证不符合脚本预期。
